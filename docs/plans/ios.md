# iOS: code signing, APNs through the proxy, Buildkite pipelines, and the app

Status: **phases 0 to 5 landed and live** (2026-11-22). TestFlight builds 38 and 39 are VALID;
sign-in works on a device with build 39. Build 40 is held. Phase 7 (screens) is built on a
branch, not landed; phase 6 (APNs) is prepared on another branch, off. Open items are listed
before the Log.

The person's words: "Design a capability to do iOS code signing from the Apple side of things.
Design a capability to do APNS notifications through the proxy. Extend the Buildkite capability
to configure an iOS build, and an iOS release pipeline. Look at noisypigeon/pigeon and create a
basic iOS app that reuses/extends the design system capability so it has the same look and
feel. The mobile app should be a 1-to-1 contract to platform.pigeon.dev but designed for iOS."

**In short.**
- **Signing.** A new `apple` capability holds the App Store Connect API key the way the proxies
  hold Cloudflare's: in the Secrets Store, read only by core, never handed out. It manages
  bundle IDs, certificates and provisioning profiles through the App Store Connect API. The
  distribution key is generated inside the Worker and kept sealed. A Buildkite macOS step trades
  its Buildkite OIDC token for a **signing session**. The session lasts at most 30 minutes, can
  be redeemed once, and works for one release. It gives the step the signing identity and
  profile, plus upload calls through an allowlisted `/apple/` proxy. The API key and a JWT never
  reach the Mac.
- **APNs.** A token-based provider (`.p8`, key id, team id) in the same capability. It has a
  device-token registry fed by the app, an `apns_send` tool, and a `/apns/` route on the proxy
  host. The proxy signs the provider JWT, sets the app's topic, picks sandbox or production per
  device, rate-limits, and handles APNs's errors (it drops a token on 410 `Unregistered`).
- **Buildkite.** Two generated pipelines: `pigeon-ios` builds and tests a branch on a macOS
  queue, and `pigeon-ios-release` archives, signs and uploads to TestFlight. Signing runs on a
  separate macOS queue. The existing setup declares and reconciles both, as it does the `pigeon`
  pipeline. **They need a macOS queue**, which Buildkite's hosted Linux queues are not.
- **The app.** SwiftUI under `ios/`, generated by XcodeGen (no binary project). It signs in
  with the platform's own OAuth, using the person's passkey on platform.pigeon.dev's page. It
  reads through the same MCP tools every other client uses. Its colours, radii, spacing and type
  are generated from `src/core/src/design/tokens.css`, the web design system's one source.

## Decisions

### 1. Where it lives

- **One new capability, `apple`**, hosted by core (`pigeon-platform`), in
  `src/capabilities/src/apple.rs` and `apple/`. Its pure parts go in `pigeon_core::apple`:
  - JWT claims;
  - the CSR's DER;
  - App Store Connect request shapes;
  - APNs request and error mapping;
  - the signing session's grant.

  Core holds the Apple keys, as it holds the parent token.
- **The proxy routes** `/apple/` and `/apns/` go in `pigeon-proxies`, beside `/git/` and
  `/cf/`, and are served by the proxy Worker. That Worker never holds an Apple key. It asks core
  over `PLATFORM` for a signed JWT for one purpose (`Purpose::Apple`, `Purpose::Apns`), as it
  asks for a scoped Cloudflare token today.
- **No new Worker.** No change to `ci/workers.toml` is needed for the capability. The `ios/`
  directory does need a lane (follow-up 8).
- **Off until configured.** With its secrets unset, the capability:
  - answers each tool with what to set and where (`docs/plans/ios.md`, follow-ups);
  - serves no route except a 404 that says so;
  - adds nothing to the Buildkite setup.

### 2. Code signing: the Apple side

**Credentials, as slots on the secrets page** (Secrets Store, scope `workers`, bound to core
only):

| Slot | What | Checked by |
| --- | --- | --- |
| `APPLE_ASC_KEY` | App Store Connect Team API key, `.p8` (PKCS#8 P-256, PEM). Role App Manager with access to Certificates, Identifiers & Profiles | signing a JWT with it and `GET /v1/apps?limit=1` |
| `APPLE_ASC_KEY_ID` | its key id | the same call |
| `APPLE_ASC_ISSUER_ID` | the team's issuer id (a UUID) | the same call |
| `APPLE_TEAM_ID` | the Developer team id (10 characters) | `GET /v1/bundleIds` lists ids with this team prefix |
| `APPLE_SEAL_KEY` | 32 random bytes, base64url, that seal the distribution key. pigeon generates it on first use. The person never types one | opening a sealed test value |

The ids are not secret, but they are Apple account identifiers, which this repository keeps out
of the tree. Keeping them in slots also keeps all five together on one page.

**The App Store Connect client** (`pigeon_core::apple::asc`):
- **One JWT per request batch.** ES256 with header `{alg: ES256, kid, typ: JWT}` and claims
  `{iss: issuer id, iat, exp: iat + 10 min, aud: "appstoreconnect-v1"}`. Apple's limit is 20
  minutes; we use 10. It is signed with WebCrypto (`ECDSA` P-256, whose raw `r‖s` output is the
  JWT signature).
- **Rate limits.** Apple sends `X-Rate-Limit` (per-hour quota). The client reads it. A 429
  answer stops the batch and reports when to retry.
- **Endpoints used:**
  - `bundleIds` (list and create) and `bundleIdCapabilities` (`PUSH_NOTIFICATIONS`,
    `ASSOCIATED_DOMAINS`);
  - `certificates` (list, create from a CSR, revoke);
  - `profiles` (list, create `IOS_APP_STORE`, delete);
  - `apps` (read; **the API cannot create an app**, so the person does that once);
  - `buildUploads`, `buildUploadFiles` and `builds` (TestFlight).

**Certificates and profiles: create, renew, list.**
- **List (read-only tool `apple_status`).** It answers:
  - whether the key works;
  - the team;
  - each bundle id pigeon manages, with its capabilities;
  - each Apple Distribution certificate, with serial, expiry and whether pigeon holds its key;
  - each App Store profile, with state, expiry and certificates;
  - what is missing.
  It reads only. Its output never holds a key or a profile's bytes.
- **Create (a console write, bound to the person's passkey, like setting a secret).**
  - "Register bundle id": `POST /v1/bundleIds`, then the two capabilities.
  - "Create signing identity":
    1. The Worker generates an RSA-2048 key pair with WebCrypto. Apple requires RSA 2048 for
       distribution certificates.
    2. It builds a PKCS#10 CSR in pure Rust (a small DER writer in `pigeon_core::apple::csr`)
       and signs it with WebCrypto.
    3. It calls `POST /v1/certificates` with `certificateType: DISTRIBUTION`.
    4. It stores the certificate with the private key sealed (below).
    5. It creates an `IOS_APP_STORE` profile for the bundle id and that certificate.
  - These are console writes, not MCP tools, so no agent can mint a signing identity. The rule
    lives in the capability itself; the policy is not changed.
- **Renew.**
  - Certificates and profiles last a year. `secret_expiry` for `APPLE_ASC_KEY` reports the
    earliest expiry among pigeon's certificate and profiles, so the existing expiry warnings
    (30 days ahead) cover them.
  - Renewal is the same "Create signing identity" write. It adds a new certificate and profile
    beside the old ones, and releases use the newest active pair.
  - "Revoke old certificate" is a separate passkey-bound write. Apple caps distribution
    certificates per team, so the console names the cap when it is near.
- **Storage.**
  - The `.p8`s are small and go in the Secrets Store as they are.
  - The distribution private key does not fit: PKCS#8 RSA-2048 is about 1.2 kB of DER, and the
    Secrets Store keeps small values. It is sealed with `APPLE_SEAL_KEY` (AES-256-GCM, as
    linked accounts seal tokens).
  - The sealed key, the certificate's DER and the profile's bytes are kept in the Directory as
    rows `apple_identities` and `apple_profiles`, keyed by Apple's ids. *As built (phase 2):*
    one Directory setting per identity, `apple:identity:{certificate id}`, holding the
    certificate, the sealed key and its profile together, and `apple:identities` listing them.
    The key is sealed with the certificate's id as associated data.
  - So the root of trust is in the Secrets Store, and nothing readable sits outside it.
  - *Departure from the brief*, which asked for certificates and profiles "stored in the Secrets
    Store". Storing them whole there was the first choice, but it would not fit. Phase 1 checks
    the Store's real value limit. If it is large enough, the certificate and profile could move
    there, and only the sealed key would stay in the Directory.

**How a Buildkite macOS agent gets a short-lived, scoped signing session.** Only the release
pipeline's `ios-sign-upload` step can get one (§4).
1. The step runs pigeon's fixed sign bootstrap, `/ci/buildkite-sign.sh`. It never runs the app's
   build scripts, so build phases and package plugins never run on a machine that holds a key.
2. The bootstrap asks `buildkite-agent oidc request-token` for a token with audience
   `https://platform.pigeon.dev/ci/apple/session` and a 300 s lifetime.
3. It presents that token at `POST /ci/apple/session` with `{release}`. Core checks:
   - the token, against Buildkite's JWKS, as `buildkite::vouched` does today;
   - that the organization is ours, the pipeline is the release pipeline, the branch is `main`,
     and the step key is `ios-sign-upload`;
   - that the build's commit is the release record's commit;
   - that the release is in state `archived` and its session has not been redeemed (one
     redemption per release);
   - that the build is on a hosted agent, when `hosted_only` is set.
4. It answers a session token `pgn_sg_…`. The token is kept as a hash, bound to
   `{release, bundle id, commit, build number}`, and lives until the earlier of 30 minutes and
   the job's end.
5. With the session token, the step may:
   - **`GET /ci/apple/identity` once.** The answer is JSON: `{certificate (DER, base64),
     private_key (PKCS#8 PEM), profile (base64), profile_uuid, profile_name, team_id, bundle_id,
     export_options}`. The step imports the key and certificate into a temporary keychain with
     a random password (`security create-keychain`, `security import`,
     `security set-key-partition-list`). It imports Apple's WWDR G3 intermediate, checked
     against a SHA-256 in the bootstrap. It writes the profile and exports the IPA
     (`xcodebuild -exportArchive`).
   - **Call the `/apple/` proxy on proxy.pigeon.dev for the upload alone.** The allowlist:
     - `GET /v1/apps?filter[bundleId]={its bundle id}`;
     - `POST /v1/buildUploads` and `POST /v1/buildUploadFiles`, for that app only (the proxy
       reads the relationship in the body);
     - `PATCH /v1/buildUploadFiles/{id}` and `GET /v1/buildUploads/{id}`, for ids made by this
       session.

     The proxy signs a fresh JWT for each call. The PUTs of the file's parts go straight to the
     presigned URLs Apple answers with, which carry no pigeon credential.
6. An `EXIT` trap deletes the keychain, the profile and the work directory. Hosted macOS agents
   are fresh machines per job, so a killed job also leaves nothing for a later job.
7. Core moves the release to `uploaded`. It polls `GET /v1/builds` (as the capability, not the
   step) until `processingState` is `VALID` (`delivered`) or `INVALID` (`failed`).

What a stolen session gives: the distribution key until the person revokes the certificate, and
upload calls for this one app until the session ends. Never the API key. Never a JWT. Never any
other App Store Connect call.

**Tools** (all read-only, so none needs the policy's `call_tool` gate):
- `apple_status`: as above;
- `ios_releases`: the latest releases and their states;
- `ios_release {commit?}`: cuts a release of main's mirrored head. It refuses while the mirror
  is behind or a release is in flight. It is not destructive and holds no secret. It still
  needs the person's word in Decisions before it is offered; until then releases start only
  after a landing that changed `ios/` deploys.

### 3. APNs through the proxy

**Credentials** (slots, core only): `APNS_KEY` (the APNs auth key, `.p8`), `APNS_KEY_ID`, and
the `APPLE_TEAM_ID` above.

**The provider token.**
- ES256 with header `{alg: ES256, kid: APNS_KEY_ID}` and claims `{iss: team id, iat}`.
- It is signed by core and cached for 50 minutes in the capability's Durable Object storage.
  APNs refuses a token older than 60 minutes and answers 429 `TooManyProviderTokenUpdates` to
  one refreshed more often than every 20.
- A 403 `ExpiredProviderToken` or `InvalidProviderToken` refreshes it once. A second 403 stops
  sending and reports.

**Apps and topics.** `settings.rs` declares the apps: `[{id: "pigeon", bundle_id:
"dev.pigeon.app"}]`. The topic is always the app's bundle id, for `alert` and `background`
pushes. A caller names the app, never the topic, so it cannot push to another app of the team.

**Sandbox and production.**
- Each registered device token records its environment: `development` for builds run from
  Xcode, `production` for TestFlight and the App Store.
- The app tells the server which: it reads `aps-environment` from its embedded provisioning
  profile at run time, and falls back to `#if DEBUG`.
- The sender posts to `api.sandbox.push.apple.com` or `api.push.apple.com` to match.
- A token sent to the wrong one answers 400 `BadDeviceToken`. It is marked, not deleted at once:
  the next registration from that device corrects it.

**The device-token registry** (Directory table `apns_devices`):
- Columns: `id`, `app`, `person_id`, `service_user_id` (the app install's OAuth client, so one
  row per install), `token`, `environment`, `created_at`, `last_ok_at`, `last_error`. It is
  unique on `(app, token)`.
- `apns_register {app, token, environment}` is an MCP tool. Only a caller acting for a person
  (an OAuth client linked to them) may call it, and it registers for that person and client.
  The app calls it after `registerForRemoteNotifications`, and again whenever the token
  changes.
- Disconnecting the app on the Access tab deletes its rows. `apns_unregister {app}` deletes the
  caller's own row.
- Tokens are never answered by a tool, logged, or put in an audit line. Audit lines carry the
  row's `id`.

**Sending.** One core function, `apns::send`, reached two ways:
- **`apns_send {app, person?, alert: {title, body}, data?, push_type?, collapse_id?}`**, an MCP
  tool. It goes to every device of `person`, or of the caller's person when unset.
  `push_type` is `alert` by default (priority 10) or `background` (priority 5, no alert,
  `content-available: 1`). `data` is a flat JSON object of short strings: links such as
  `pigeon://approvals`, never a secret or a token. The payload is checked against APNs's
  4 KB limit before sending.
- **`POST https://proxy.pigeon.dev/apns/{app}/send`**, the same body. It is for a cloud session
  or a CI job, and takes a proxy credential, or a job token whose grant names `apns`. The proxy
  Worker asks core for the provider token (`Purpose::Apns`). It never sees the `.p8`, and it
  reads device tokens from core per send. The caller sees neither.
- The platform's own events go through the same function: a tool call waiting for the person's
  passkey, a landing that failed, a run's question. They use `collapse_id`s such as
  `approval:{id}`.

**Rate limits.**
- Per person and app: 30 sends a minute and 500 a day, counted in the capability's Durable
  Object.
- Per device: one `collapse_id` at a time. A newer push with the same id replaces the older one
  on the phone.
- APNs's 429 `TooManyRequests` for a device backs that device off for 10 minutes.

**Errors, as APNs answers them:**

| Answer | What pigeon does |
| --- | --- |
| 200 | record `last_ok_at`; answer the `apns-id` |
| 400 `BadDeviceToken` | mark the row; delete it if its environment was already corrected once |
| 400 `DeviceTokenNotForTopic`, `BadTopic`, `TopicDisallowed` | stop: the key or bundle id is wrong; report to the person |
| 400 `PayloadEmpty`, 413 `PayloadTooLarge` | refuse to the caller (checked first, so rare) |
| 403 `ExpiredProviderToken`, `InvalidProviderToken` | refresh the token once, then report |
| 410 `Unregistered` / `ExpiredToken` | delete the row when APNs's `timestamp` is later than its `created_at` (the app removed or reinstalled) |
| 429 `TooManyProviderTokenUpdates` | keep the cached token; report |
| 429 `TooManyRequests` | back that device off 10 min |
| 500, 503 `ServiceUnavailable`, `Shutdown` | retry twice with backoff through the platform's queue, then report |

**Open point: HTTP/2.** APNs speaks only HTTP/2. noisypigeon's control plane sent APNs from a
Worker, but this plan has not confirmed that a Worker's `fetch` reaches APNs over HTTP/2. Phase 6
proves it first with one push to a development device. If it fails, the sender moves into a
container (the CI base image's curl speaks HTTP/2), started by the same Durable Object. The tool
and the route do not change.

**As built (phase 6 prep, not landed).**
- `pigeon_core::apns` holds the pure parts: the provider token's signing input, the 50 and 20
  minute cache rule, the host per environment, the device-token form, the payload builder with
  the 4096-byte check, the request headers, the error table as `action(status, reason)`, and the
  rate-limit count. The smoke scenario `apple_apns_payload_errors_and_registry` covers them.
- Built on the capability side, all off until the key is set: slots `APNS_KEY` (checked as a
  .p8 that signs an ES256 token) and `APNS_KEY_ID` on the `apple` capability; the Directory table
  `apns_devices` (one row per app and client) with ops `apns.register`, `apns.unregister`,
  `apns.devices`, and `app.disconnect` deleting the client's rows; tools `apns_register`,
  `apns_unregister`, `apns_status` and `apns_send`. `apns_send` sends nothing and says what to
  set while `APNS_KEY`, `APNS_KEY_ID` and `APPLE_TEAM_ID` cannot be read. Tokens are never
  answered, logged or audited. The signing and sending itself lands with phase 6b.
- No wrangler binding is added now: a binding to a missing Secrets Store secret fails the
  deploy (Log, phases 1a and 1b). The bindings land as phase 6b.
- HTTP/2 spike: from the sandbox, `curl --http2` to the sandbox host with no token answered
  `HTTP/2 403`, an `apns-id`, and `{"reason":"MissingProviderToken"}`. `apns_status` with
  `probe: true` now does the same from the Worker's `fetch` and answers the status, `apns-id`
  and reason; a 403 or 400 with an `apns-id` means the Worker speaks HTTP/2 to APNs. The
  result is still to read once deployed.
- Design for the route, a departure from the text above: the proxy Worker stays key-free and
  token-free. `POST /apns/{app}/send` only authenticates the proxy credential or a job token
  whose grant names `apns`, then forwards to core's single sender (an `apns.send` op over
  PLATFORM). Core signs and sends. Until core's setting `apns_route = false` is flipped, the
  route answers 404 saying APNs is not set up.

**As built (phase 6b, not landed; Log 2026-11-23).**
- Core binds `APNS_KEY_ID` and `APNS_KEY` (`APPLE_TEAM_ID` was already bound). No other Worker
  binds them.
- The provider token is signed with `pigeon_core::apple::sign_es256` (split out of `sign_jwt`)
  and cached in the Directory setting `apns:provider-token` for 55 minutes, with its key id and
  team. It is reused under 50 minutes and re-signed when the key id or team changes.
- `apns_send` sends to every device of `person`, or of the person the caller acts for. The
  answer holds row ids and outcomes, never a token. Departures from the table above:
  - A 400 `BadDeviceToken` drops the row at once. The app registers again on every launch, so
    a token sent to the wrong environment comes back corrected.
  - A 500 or 503 is retried twice inline (300 and 600 ms), not through the platform's queue.
  - The rate limit counts calls in the Directory setting `apns:sends:{app}:{person}`. Two
    calls at the same moment can both pass.
  - Any caller the policy lets call `apns_send` (rule `tools-run`) may name any person.
- The app asks to allow notifications once signed in, registers with APNs, and calls
  `apns_register` with the environment from its embedded profile (Debug: development, Release:
  production). It carries `aps-environment` (development in the project; `ios/ci/release.sh`
  sets production before signing).
- `/apple/release/identity` now makes sure the profile it hands out carries Push. It adds
  `PUSH_NOTIFICATIONS` to the bundle id if missing. If the held profile lacks
  `aps-environment` or Apple says it is not ACTIVE, it makes a new App Store profile for the same
  certificate. It deletes and changes nothing.
- An approval waiting for a passkey can push to the approver (`push::NOTIFY_APPROVALS`, off).

### 4. Buildkite: the iOS pipelines

The generator is built tonight, off, as `pigeon_ci::buildkite::ios`. Phase 3 wires it in.

- **Settings.** `Buildkite` gains `ios: Option<Ios>`, which is `None` until the person turns it
  on. `Ios` names:
  - the platform host;
  - the two pipeline slugs, `pigeon-ios` and `pigeon-ios-release`;
  - two macOS queues: `pigeon-macos`, which builds, and `pigeon-macos-sign`, which only signs
    and uploads;
  - the release branch, `main`.
- **The agent requirement.** Both queues need **macOS agents with the Xcode of
  `ios/.xcode-version`**. The setup today makes hosted Linux queues only. With `ios` set, it adds
  the two queues:
  - **hosted**, with a macOS instance shape, if the organization's Buildkite plan offers hosted
    macOS (the shape's exact name is read from Buildkite's queue API in phase 3; it is not
    confirmed here);
  - **self-hosted**, if not: a queue with no shape, served by a Mac the person runs
    `buildkite-agent` on, with tags `queue=pigeon-macos` (follow-up 6).

  Hosted agents are better for `pigeon-macos-sign`, because each job gets a fresh machine.
- **`pigeon-ios`, the build pipeline**, for session branches before they land and for `main`.
  - Step `ios-check`: queue `pigeon-macos`, timeout 60 min.
  - It runs the same bootstrap as `pigeon` (`/ci/buildkite.sh`: OIDC token → job token → fetch
    the commit through the git proxy → report). The Mac never holds a repository credential.

### 5. The iOS app

**What it is.**
- SwiftUI for iOS 18, in `ios/`, with the project generated by XcodeGen from
  `ios/project.yml`. The `.xcodeproj` is never committed.
- Bundle id `dev.pigeon.app`, display name "Pigeon". It takes over the old app's records (§6).
- **It cannot be compiled on Linux.** `sh ci/runner/test.sh` never builds Swift. The Rust gate
  checks only that the generated tokens file matches `tokens.css` (smoke scenario
  `platform_design_tokens_for_ios`). Swift is compiled only by `pigeon-ios` on a macOS agent,
  from phase 3, or on the person's Mac.

**A 1:1 contract with platform.pigeon.dev.** The app talks to the platform the way every non-browser
client does. It adds no app-only API.
- **Sign-in is the platform's OAuth, with the person's passkey on the platform's own page.**
  1. On first run the app registers itself: `POST /oauth/register` with
     `{client_name: "Pigeon for iOS", redirect_uris: ["https://platform.pigeon.dev/app/oauth"]}`.
     Each install is its own client, so each phone is its own "app" on the Access tab and can be
     disconnected alone.
  2. It opens `/oauth/authorize` (PKCE S256, `state`) in `ASWebAuthenticationSession`, with an
     **HTTPS callback** (`.https(host: "platform.pigeon.dev", path: "/app/oauth")`). The person
     signs in with their passkey on the platform's page, as Claude's connector does.
  3. It exchanges the code at `/oauth/token`. Tokens are kept in the Keychain
     (`AfterFirstUnlockThisDeviceOnly`). The 1 h access token is refreshed with the 30 d refresh
     token, and a second 401 signs out.
  - Why HTTPS and not a `pigeon://` scheme: the platform accepts only HTTPS or loopback
    redirects, and an HTTPS callback that only the associated app can claim is the safer form
    for native apps (RFC 8252 §7.2). So the contract stays unchanged.
  - Its cost: `/.well-known/apple-app-site-association` must list the app (phase 5).
- **Why not the console's cookie.** The console session is shaped for a browser: SameSite,
  the Origin check, 30 minutes idle. OAuth is the platform's contract for every other client. It
  gives per-device revocation and needs nothing new on the server.
- **Data is MCP**: `POST /mcp` with the bearer token, JSON-RPC `initialize` then `tools/call`.
  The app reads `structuredContent`, or the JSON in `content[0].text` for lists. Each console
  section maps to a tool:

| Console tab and section | MCP tool the app calls | Phase |
| --- | --- | --- |
| Sign-in (icon, one line, the button) | OAuth above | 0 (skeleton) |
| Access › passkeys | `passkeys_list` | 0 (skeleton: the read-only list) |
| Access › people, apps | `users_whoami`, `users_list`, `oauth_clients` | 7 |
| Approvals › waiting for you | **gap**: needs `approvals_list` (today the section is console-only), then `approvals_status {id}` | 7 |
| Architecture | `architecture_describe` | 7 |
| Cost | `models_usage` | 7 |
| Landings and CI (agents' view) | `land_status`, `ci_status`, `ci_jobs` | 7 |
| AI agents | `ai_agents_status`, `ai_agents_inbox`, `ai_agents_answer` | 7 |
| Push | `apns_register`, `apns_unregister` | 6 |

  - Writes that need the person's passkey (approving a gated tool call, issuing a credential)
    use the same ceremony routes the console uses. Until native passkeys exist (phase 7), the app
    opens the console's page for them in `ASWebAuthenticationSession`.
  - Phase 7 asserts natively with `ASAuthorizationPlatformPublicKeyCredentialProvider` for
    relying party `platform.pigeon.dev`, which the `webcredentials` association allows. The
    platform's verifier already accepts the origin a native assertion carries.
  - The app calls no gated tool directly.
- **Design tokens, generated, not copied.**
  - `pigeon_core::design::swift` reads `tokens.css` and writes `ios/Pigeon/Design/Tokens.swift`:
    - every colour as a light/dark dynamic `Color`;
    - radii, spacing, the grid step and the dot size as `CGFloat`;
    - each `--type-*` as a `TypeToken` (weight, size, line height, sans or mono). SF Pro and
      SF Mono are what the web stack's `-apple-system` and `ui-monospace` resolve to on Apple
      platforms.
  - A token of a shape it does not know is an error, not silently dropped.
  - Regenerate with `cargo run -q -p pigeon-capabilities --example design_swift --target
    x86_64-unknown-linux-gnu`. The smoke suite fails when the committed file differs.
  - `Components.swift` builds the shared pieces from the tokens only: the dot grid, the
    hard-shadow card, the mono eyebrow and the accent button. They follow noisypigeon's
    `Theme.swift`, so the look carries over without its hand-copied hex values.
- **What the skeleton does** (phase 0):
  - signs in as above and shows the passkeys list read-only, with pull to refresh and sign-out;
  - writes nothing;
  - until phase 5 serves the association file, a device cannot complete sign-in (the callback
    is not claimed). `ios/README.md` says so.

### 7. Who may take a release's steps (phase 4)

Approved by the person on 22 November 2026: "check main's head only at /apple/release/start,
then trust the release record's commit for the identity and upload steps".

- **Every step** needs the job's own live token, for a running CI job `ios-release` on
  Buildkite (whose exchange takes hosted agents only).
- **`/apple/release/start`** also needs the job's commit to be main's head, and no other release
  open. It then records the release under the job's id, with that commit. A job that already
  has a record for its commit gets the same answer again, without a new head check: the record
  shows it started at main's head.
- **`/apple/release/identity` and `/apple/release/upload`** do not read main's head. They need
  this job's own release record (records are kept by job id, so a job cannot reach another
  job's), with the job's commit, still open, and not past the record's expiry (2 hours since
  its last step). The steps' order is unchanged: identity once, then the IPA once.
- So a branch still never obtains the signing identity: only a job whose release started at
  main's head can continue. Main moving during the release no longer stops it.
- One release at a time and the 2-hour expiry stay as they were.
