# iOS billing and upgrade notices (phase 5)

Status: landed (`27a47c5`, with the follow-up `ab69007`). Phase 5 of [ios-billing-settings.md](ios-billing-settings.md).

Needs you remains the place for questions, decisions and passkey approvals. Add two read-only sections, with no approval, dismissal or upgrade action. Count one notice per grant or per instance/component update in the shared detail, Sessions card and tab badge. Before the first detail visit those counts cover only the ordinary inbox; opening the detail discovers notices. Keep the notice counts on return to Sessions. Do not say everything is caught up while a section is loading or failed.

- **Grants expiring soon.** Read only `cost_daily.credits.grants`, the promotional ledger, never purchased credit totals. Use the returned name and positive `remaining` in USD; do not calculate a balance. `expiry` is a UTC calendar date, inclusive. Show day 0 through day 7 inclusive, warning on days 0 through 3. An empty configured list is valid; missing or invalid grant data is unavailable.
- **Breaking capability updates.** Read `capabilities_upgrade_plan` once for all instances, using its `instances[].steps` and the phase 4 step decoder. A step counts when `work` has entries (including pre-1.0 breaks) or the target major differs from the selected version or held pin. Show the plan's component, instance and target, with the returned work summaries. Use the already-loaded instance titles when available. The plan is sufficient for a notice, not permission to change a pin.

Fetch each source independently on detail opening or pull to refresh. Root, Sessions and inbox actions keep their existing reads and never start a notice fetch. When opening, reuse a recent same-UTC-day Cost payload from the signed-in client if available; otherwise use one `cost_daily` request for `today`, the narrowest range. Pull to refresh bypasses the cache. Capture the payload at the existing client boundary without changing normal Cost calls or proposal validation. Clear it and the notice state on sign-out. Fail each source separately with a short retry message; do not expose server error text or log payloads.

Review with `ios-check`. On a simulator with real tool data, verify UTC days 0/3/7 versus past and day 8, exhausted/absent grants, a same-major step with work, a major change with empty work, and a patch with no work. Check that a failure of either tool does not hide the inbox or the other section, that the three counts agree, and that navigation and approval/answer do not trigger a background Cost refresh. Do not seed example grants in the live config.
